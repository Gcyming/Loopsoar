# ADR-0155 新标签页快捷方式与自定义协议拦截

日期：2026-11-28
状态：已采纳

## 背景

用户提出两件事（m04220）：

1. 新标签页搜索框下那排图标**本来应该是「快捷方式」**（Chrome/Edge 的快捷方式磁贴），而现在它只是
   「最近访问」的历史镜像：不可添加、不可编辑，还会随浏览记录漂移。参照图三/图四，应当有一个
   主动的「+」入口，添加后能改名、改址、删除。
2. 打开某些网页时会弹出 Windows 系统对话框「获取打开此'bitbrowser'链接的应用 / 你的电脑没有可打开此链接的应用」。

## 决策一：快捷方式独立于历史

- 新增 `ShortcutsStore`（`packages/shell/src/main/shortcutsStore.ts`），落盘 `<dataDir>/shortcuts.json`，
  结构 `{ version: 1, items: [{ id, url, title, icon?, createdAt }] }`。
- 规则与书签一致：URL 规范化（只写 `example.com` 时补 `https://`）、同 URL 去重、
  原子写（tmp + rename）、解析失败改名 `<file>.corrupt-<ts>` 隔离现场、上限 24 条淘汰最早添加的。
- 图标：只在缺 `icon` 时抓一次 `resolveFavicon` 并写回存储，之后打开新标签页不再联网；
  抓不到就用首字母块。
- IPC 面：`shortcuts:list / add / update / remove / pin`（`pin` = 移到最前），全部 `sensitive: true`。
- UI：`StartPageShortcuts.tsx` 渲染磁贴网格，末尾固定「+」磁贴；右键菜单提供
  编辑 / 移到最前 / 删除；添加弹窗可从历史里的常见站点一键填充（历史只作建议来源，不自动变成快捷方式）。
- 历史记录本身不动：`browser-history.json` 仍是全局历史，两套数据互不影响。

## 决策二：标签页内只允许网页协议

根源：页面里一个 `<a href="bitbrowser://…">` 或被脚本改写的 `location`，Chromium 会把它交给操作系统；
Windows 找不到注册该协议的应用程序，就弹出「没有可打开此链接的应用」系统对话框。

- 新增 `isInTabNavigationAllowed(url)`（`packages/shell/src/main/electronBrowser.ts`）：
  放行 `http:` / `https:` / `about:blank` / `blob:`，其余（`bitbrowser:`、`mailto:`、`file:`、`javascript:` 等）一律拦截。
- 两个拦截点：
  1. 每个标签视图的 `will-navigate` 与 `will-frame-navigate`（`preventDefault`）；
  2. `webRequest.onBeforeRequest` 的 `mainFrame` 兜底（`cancel`）——渲染层被绕过时仍不会到达系统。
- 应用自己的 `loadURL`（`file://` 文档预览、`about:blank` 新标签）不触发 `will-navigate`，行为不变。
- 拦截是静默的（与 `window.open` 非 http(s) 的处理一致）：不弹应用内提示，也不调用 `shell.openExternal`，
  避免把浏览器变成协议启动器。

## 后果

- 新标签页第一屏由用户自己决定；历史仍然是历史，但不再偷偷占用这一屏。
- 网页无法再通过自定义协议唤起本机应用，也就不会有系统级弹窗；代价是 `mailto:` 之类站内链接点了没反应
  （需要时可另做「用户显式点击 → 询问后交给系统」的路径）。
- `shortcuts.json` 与 `closed-tabs.json` 都是旁路数据：损坏只影响该功能，不阻断启动。
- `types.d.ts` 触到 1400 行预算，终端类型面拆到 `terminalTypes.ts`（原文件再导出，导入方零改动）。
