# ADR-0145 扩展运行时：子进程隔离 + 工具桥接

- 日期：2026-10-31
- 状态：✅ 已验证（v3：单测覆盖 semver/兼容/依赖/签名/ZIP/安装回滚/市场目录签名/撤销/富 UI 协议 + 真机 E2E：`docs/screenshots/gui-46-extension-runtime.png`）
- 关联：ADR-0144 三体隔离（扩展/技能/MCP 独立目录与通道）

## 背景
扩展此前只做到「发现 / 启停 / 卸载」：清单里的 `main` 入口从未被加载，工具也没有进入 Agent 工具表。
用户明确要求扩展可用，同时 Loopsoar 的承重约束是：扩展是第三方代码，**不能**与主进程共享生命周期，
更不能绕过沙箱/权限确认（slime 的扩展实现正是在主进程直接执行，导致崩溃面与权限面失控，属于不能照搬的部分）。

## 决策
1. **每个扩展一个独立 Node 子进程**（`extensionWorker.mjs`），主进程通过 stdin/stdout 行分隔 JSON 协议通信；
2. 扩展模块契约：`export async function activate(api)`（或 `default`），`api.registerTool({ name, description, parameters, permissions, execute })`；
3. 工具以 `ext__<扩展id>__<工具名>` 注册进全局 `ToolRegistry`；`parameters` 使用扩展声明的 JSON Schema（不再占位为空），
   权限按声明的类别映射，**实际执行仍走沙箱与确认流程**（未知工具名 deny 兜底）；
4. 生命周期隔离：启动超时 8s、调用超时 20s；崩溃/退出/超时 → 注销该扩展全部工具并标记 `error`，不影响其它扩展与主进程；
5. 工具集变化回调 `onToolsChanged` → 刷新沙箱已知工具；否则新工具会被沙箱判「未知工具名（不在注册表）」而拒绝；
6. **API 版本协商**：清单 `apiVersion`（缺省 1.0.0）决定可用能力。宿主 API 2.0 支持事件与富 UI；1.x 只保留工具桥；
   worker `ready` 回报 `protocol`，声明了 `events` 却只支持协议 1 的扩展直接启动失败，避免「声明了钩子但永远收不到」；
7. **依赖图与版本**：`dependencies` 用 SemVer 范围声明，宿主做拓扑排序/环检测/缺失与版本校验；
   启用时自动启用依赖闭包，禁用/卸载时级联禁用依赖者；任何依赖错误 fail-closed（扩展标 blocked，不启动）；
8. **签名与信任**：manifest 可带 Ed25519 分离签名；包摘要覆盖全部文件（路径+长度+内容）。信任库持久化公钥指纹，
   指纹必须由公钥重算，渲染层不能伪造。策略 `warn`（默认：未签名可运行但标 unverified）与 `strict`（只有已信任签名可运行）；
   签名/摘要无效一律 blocked，任何策略都不放行；
9. **安装 / 更新 / 回滚 / 市场**：安装走 `.staging` → 校验 → `.backups` → 原子 rename，失败自动还原；
   支持目录与 ZIP（安全读取：拒绝路径穿越/symlink/加密/ZIP64，限制条目数与解压体积，校验 CRC）；
   市场是静态 JSON registry，下载地址只允许 http(s)（每一跳重定向重新校验），包必须带 sha256，体积上限 64MB；
10. **富 UI 与事件钩子**：清单可声明 `views`（HTML 入口）与 `events`（`turn.start/turn.end/tool.before/tool.after`）。
    视图由 `loopsoar-ext://<id>/<path>` 协议提供，跑在 `sandbox="allow-scripts"` 的 iframe 中，
    响应注入严格 CSP（`default-src 'none'`、`connect-src 'none'`），与主界面不同 origin；
    视图消息由 `api.onViewMessage(viewId, handler)` 按 viewId 路由（不占生命周期事件名）；
    `turn.start` 可返回 `promptAppend` 注入 volatile 段，`tool.before` 可否决工具调用（只能否决，不能放行）；
    钩子异常/超时 fail-open，安全边界仍是工具权限/沙箱/确认；
11. **兼容性认证**：每次扫描产出 `certified / compatible / unverified / blocked`：
    签名已信任 + 零警告 + 固定 engines + 依赖满足 = certified；兼容但有警告 = compatible；
    未签名/签名未信任 = unverified；API 不兼容、依赖错误、签名无效或 strict 策略未信任 = blocked。
12. **市场运营与止损（v3）**：目录 `index.json` 可带 Ed25519 签名、`expiresAt`、`channel` 与 `revocations`。
    客户端配置市场公钥后强制 trusted 签名，未签名/非受信目录直接拒绝；过期目录拒绝；撤销记录持久化到
    `extensions-revocations.json` 并单调累积（省略不复活），命中 `id/version` 的扩展在重扫时强制 blocked 并停 worker；
    信任密钥支持 `notBefore/notAfter/revokedAt`，撤销保留审计记录但立即退出有效信任集；
    发布侧用 `pnpm market:keygen/build/sign/verify` 从 zip 目录生成并签名目录，全程静态托管、零服务器。

## 理由
- 子进程是「崩溃/死循环/阻塞」最直接有效的隔离边界，且 Node 进程模型与扩展作者心智一致（ESM 模块）；
- 行分隔 JSON 比 IPC/原生插件简单、可测试、跨平台一致；
- 权限不因扩展而放松：扩展只是「提供工具定义」，执行决策仍由 Loopsoar 的沙箱/权限层掌握（fail-closed）。

## 替代方案
- **主进程动态 import 扩展**（slime 方式）：否——第三方代码可 `process.exit`、阻塞事件循环、污染全局；
- **worker_threads**：隔离内存但共享进程信号与原生崩溃风险，且无法硬超时 kill；
- **受限 VM/QuickJS**：安全性更好但生态兼容性差、工具生态无法使用 Node 库，收益/成本不匹配当前阶段。

## 验证方式
- `tests/core/semver.spec.ts`、`extensionCompat.spec.ts`、`extensionGraph.spec.ts`、`extensionSignature.spec.ts`：版本/兼容/依赖/签名纯逻辑；
- `tests/shell/extensionTrust.spec.ts`、`zip.spec.ts`、`extensionInstaller.spec.ts`、`extensionProtocol.spec.ts`：
  信任库、ZIP 安全读取、安装/升级/回滚、富 UI 协议与 CSP；
- `tests/core/registrySignature.spec.ts`、`tests/shell/extensionMarket.spec.ts`：目录签名/篡改/过期/撤销/密钥撤销与真实 HTTP 安装链路；
- `tests/shell/extensionRuntime.spec.ts`：真实 worker 子进程 → 工具注册/JSON Schema/调用/停止注销；坏扩展崩溃隔离；
  纯声明式扩展启动为 ready（不 spawn worker）；
- 真机 E2E：`.loopsoar-data-mock/extensions/demo`（注册 echo 工具）→ Agent 调用 `ext__demo__echo` → 工具卡显示「完成 / 扩展 echo: hello-ext」并回灌模型（gui-46）；
- 富 UI E2E：`pnpm e2e:extension` → `loopsoar-ext://` 沙箱 iframe 发出 ready/resize、`viewMessage` 回包 ok，
  截图 `e2e-evidence/p2-extension-panel.png`；同时覆盖主界面 CSP `frame-src loopsoar-ext:` 与沙箱 opaque origin 的 postMessage 校验；
- 沙箱同步回归：MCP / 扩展工具动态注册后不再被「未知工具名」拒绝。

## 回退条件
若子进程方案导致扩展生态不可用或性能不可接受（冷启动 > 2s 持续），回退到「主进程加载 + 独立权限令牌」方案，
但必须保留：工具注册走 ToolRegistry、权限走沙箱、单扩展失败不影响其它扩展。
