# ADR-0008 扩展运行时：子进程隔离 + 工具桥接

- 日期：2026-10-31
- 状态：✅ 已验证（单测 3 项 + 真机 E2E：`docs/screenshots/gui-46-extension-runtime.png`）
- 关联：ADR-0007 三体隔离（扩展/技能/MCP 独立目录与通道）

## 背景
扩展此前只做到「发现 / 启停 / 卸载」：清单里的 `main` 入口从未被加载，工具也没有进入 Agent 工具表。
用户明确要求扩展可用，同时 Loopsoar 的承重约束是：扩展是第三方代码，**不能**与主进程共享生命周期，
更不能绕过沙箱/权限确认（slime 的扩展实现正是在主进程直接执行，导致崩溃面与权限面失控，属于不能照搬的部分）。

## 决策
1. **每个扩展一个独立 Node 子进程**（`extensionWorker.mjs`），主进程通过 stdin/stdout 行分隔 JSON 协议通信；
2. 扩展模块契约：`export async function activate(api)`（或 `default`），`api.registerTool({ name, description, parameters, permissions, execute })`；
3. 工具以 `ext__<扩展id>__<工具名>` 注册进全局 `ToolRegistry`；`parameters` 使用扩展声明的 JSON Schema（不再占位为空），
   权限按声明的类别映射，**实际执行仍走沙箱与确认流程**（未知工具名 deny 兜底）；
4. 生命周期隔离：启动超时 8s、调用超时 20s；崩溃/退出/超时 → 注销该扩展全部工具并标记 `error`，不影响其它扩展与主进程；
5. 工具集变化回调 `onToolsChanged` → 刷新沙箱已知工具；否则新工具会被沙箱判「未知工具名（不在注册表）」而拒绝；

## 理由
- 子进程是「崩溃/死循环/阻塞」最直接有效的隔离边界，且 Node 进程模型与扩展作者心智一致（ESM 模块）；
- 行分隔 JSON 比 IPC/原生插件简单、可测试、跨平台一致；
- 权限不因扩展而放松：扩展只是「提供工具定义」，执行决策仍由 Loopsoar 的沙箱/权限层掌握（fail-closed）。

## 替代方案
- **主进程动态 import 扩展**（slime 方式）：否——第三方代码可 `process.exit`、阻塞事件循环、污染全局；
- **worker_threads**：隔离内存但共享进程信号与原生崩溃风险，且无法硬超时 kill；
- **受限 VM/QuickJS**：安全性更好但生态兼容性差、工具生态无法使用 Node 库，收益/成本不匹配当前阶段。

## 验证方式
- `tests/shell/extensionRuntime.spec.ts`：真实 worker 子进程 → 工具注册/JSON Schema/调用/停止注销；坏扩展崩溃隔离；纯声明式扩展报错；
- 真机 E2E：`.loopsoar-data-mock/extensions/demo`（注册 echo 工具）→ Agent 调用 `ext__demo__echo` → 工具卡显示「完成 / 扩展 echo: hello-ext」并回灌模型（gui-46）；
- 沙箱同步回归：MCP / 扩展工具动态注册后不再被「未知工具名」拒绝。

## 回退条件
若子进程方案导致扩展生态不可用或性能不可接受（冷启动 > 2s 持续），回退到「主进程加载 + 独立权限令牌」方案，
但必须保留：工具注册走 ToolRegistry、权限走沙箱、单扩展失败不影响其它扩展。
